# Durable knowledge criteria

## Architecture decision record

Create an ADR when a decision is consequential, has plausible alternatives, and constrains future implementation. Record context, decision, alternatives considered, consequences, and status. Do not create an ADR for a routine library call or a choice obvious from repository convention.

## Domain glossary

Add or revise a term when one concise canonical meaning will improve conversation, naming, tests, and documentation. Include relationships and invariants when they prevent ambiguity. Prefer the repository's existing glossary location.

## Behavioral documentation

Update instructions or references used by users, operators, or integrators when their observable workflow changes. Protected top-level files still require permission.

## Code comments

Comment why a surprising constraint exists, why an obvious alternative is unsafe, or what external invariant the code must preserve. Let names, types, and structure explain ordinary behavior.
